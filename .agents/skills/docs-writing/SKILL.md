---

# 写作目的

- 文档面向想了解项目概况的人，用户文档不是代码注释。

# 写作过程

- 不执行版本控制操作，改动留在工作区。
- 有疑问先向用户提问，不自行猜测。
- 统一复查全部描述的风格，而不是只修改被点名的位置。
- 修订后执行格式化检查。
- 复查相对链接与外部链接是否有效。
- 新增链接前先核验可达性。

# 写作风格

- 使用陈述句，不用口语化表达，不加语气加重，不写元叙述与闲话。
- 不把需求方口吻的句子写进文档，约束改写成事实陈述。

# 写作内容

- 不出现真实的生产或测试环境地址、账号与凭据，只使用占位符与保留示例地址。
- 说明服务或工具做什么、使用者需要配置什么，不说明内部如何实现。
- 删除方法名与调用链、源码路径、内部流程与模块划分、内部数据结构、实现细节、覆盖率与路线图。
- 保留硬编码的常量类信息，例如配置项名称与默认值、错误码与状态码、协议关键字。
- 尚未完成或尚未验证的内容改写成简短的「当前限制」事实段落。
- 每份文档只围绕自己的主题展开，越界的内容压缩为一句结论并附指向归属文档的链接。
- 同一件事只在一处描述，不重复描述同一个对象。
- 不在正文展开配置项的作用；含义与完整清单集中在配置参考文件里。
- 各文档只保留与自身主题相关的配置表，列出名称与默认值，不写散文式解释。
- 库与工具的选项旁附官方参考链接。

# 结构排版

- 章节顺序按整体到局部、逻辑先后或时间先后、重要到次要排列；以操作步骤为主的文档保持执行顺序。
- 每段描述放在最合适的章节里。
- 章节不编号，交叉引用使用描述性链接。
- 单元格内容多而长的表格改为列表，或缩减内容后移到别处。
- 层级关系用列表表达。
- 占位与插值统一使用 `${var}` 形式，真实代码语法除外。
- 外链清单按主题分组，每组只给入口链接，不逐条罗列同一对象的全部接口。
