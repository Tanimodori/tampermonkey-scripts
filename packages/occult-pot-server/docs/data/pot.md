# Pot 数据

「罐子」（pot）是魔法罐刷新时间表里的一行。本文说明这张表的列、表内派生列、清洗规则，以及「30 分钟刷新」这条时间规律。

## 1. 服务管理的五个数据列

表格按表内顺序排列。智能表的 `values` 以**列标题**为键，API 侧使用下表的字段名。

| 列标题             | API 字段           | 含义                 | 规则                                                   |
| ------------------ | ------------------ | -------------------- | ------------------------------------------------------ |
| `区服`             | `world`            | 所在区服             | 只能是 `鸟`、`猫`、`猪`、`狗`                          |
| `地图`             | `map`              | 所在岛屿             | 只能是 `北岛`、`南岛`                                  |
| `ID`               | `potId`            | 罐子的游戏内 ID      | 形如 `54-1-4000E8F3`，即 `^\d+-\d+-400[0-9A-Fa-f]{5}$` |
| `北罐刷新时间`     | `northRefreshAtMs` | 北罐的下一次刷新时刻 | 13 位 epoch **毫秒**；`0` 视为无效                     |
| `最后一次进岛时间` | `lastVisitAtMs`    | 最后一次进岛的时刻   | 13 位 epoch 毫秒                                       |

时间在表格里按 UTC+8 显示，存储与传输一律用 epoch 毫秒。

## 2. 单元格取值形态

- **读取**：文本/链接/选项类单元格会以数组返回，两列时间是字符串形式的毫秒数。服务读取时把各种形态都归一：文本走 `parseCellText`（数组、原始值、字符串都接受），时间走 `parseCellEpochMs`（解析不出来就是 `0`，随后按无效行丢弃）。
- **写入**：文本列一律写**裸字符串**（`"鸟"`），两列时间写成字符串形式的毫秒数。读取比写入宽容：表里回给我们的文本列可能是 `[{"type":"text","text":"鸟"}]`，服务在读取时把它拆成文本。

各类单元格的形态：

| 单元格类型    | 形态                                     |
| ------------- | ---------------------------------------- |
| 文本          | `[{"type":"text","text":"鸟"}]`          |
| 链接          | `[{"type":"url","text":"…","link":"…"}]` |
| 选项          | `[{"text":"鸟"}]`                        |
| 数字 / 复选框 | 原始 `number` / `boolean`                |
| 日期          | epoch 毫秒的字符串                       |

## 3. 表内额外的三列

`罐子在什么时间刷新`、`罐子还有多久刷新`、`上次进岛时间（几分钟前）` 由表格自己的公式算出，**只供人阅读**：它们不存储、不写入，也不出现在任何 API 载荷里。客户端只会拿到原始的 `北罐刷新时间` 与 `最后一次进岛时间` 两个 epoch。

## 4. 30 分钟刷新逻辑

罐子的刷新周期是一个常量：**C = 1804 秒（30 分 04 秒）**。同一个罐子的北罐刷新时刻因此构成等差序列 `n, n+C, n+2C, …`；已知其中任意一次 `n` 时，下一次刷新是：

```
n + ceil((now - n) / C) * C
```

同一座岛上，一轮里的南罐比北罐晚 `C`。既有客户端脚本据此把「南」位置的时间戳减去 `1804` 秒，归一到本轮北罐时刻，并按下面的 Fate ID 判断记录属于哪个罐位：

| Fate ID | 罐位     |
| ------- | -------- |
| `0x7B8` | 南岛北罐 |
| `0x7B9` | 南岛南罐 |
| `0x818` | 北岛北罐 |
| `0x819` | 北岛南罐 |

以上都是**背景知识**，用来解释表里那一列的含义。服务端只原样存储与返回 `北罐刷新时间`，不计算任何排期，也不推断下一次刷新时刻。

## 5. 数据清洗规则

清洗（去重、过期删除、无效行删除）是客户端脚本的职责；服务端只做「不合格行直接丢弃」，**既不去重也不做过期删除**。

- 唯一行键是 `区服|地图|ID`。表里出现重复时，保留 `最后一次进岛时间` 更大的那一行。
- `最后一次进岛时间` 早于 3 小时（`10800000` 毫秒）即视为过期，删除。
- `北罐刷新时间` 为 `0`、缺失或格式不对的行不是有效的罐子，删除。

服务端读到这类行时同样不会把它当成一个罐子：`区服`/`地图`/`ID` 不合规，或两个时刻不是 13 位毫秒的行，在映射阶段就被丢掉（见 `../api/upstream.md`），下游永远看不到它们。区别在于服务端不做删除与去重 —— 表里已有的重复行、过期行会照原样返回，直到某个变更触及它（见 `store.md`）。
